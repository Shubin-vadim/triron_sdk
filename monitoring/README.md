# Monitoring

```bash
docker compose --profile openai --profile monitoring up -d
uv run python examples/load.py --concurrency 8 --requests 200   # so there's something to look at
```

| Where | What |
|---|---|
| http://localhost:3000 | Grafana, the **Triton → Triton LLM** dashboard opens right away (anonymous admin, no login) |
| http://localhost:9090 | Prometheus: raw metrics, `Status → Targets` shows what's being scraped |
| http://localhost:9000/metrics | what Triton exposes (OpenAI profile); http://localhost:8002/metrics — for `native` |

## Where the metrics come from

- `nv_*` — Triton core: request counters (`success` / `failure`), per-stage durations (queue → input → infer →
  output) in **cumulative microseconds**, queue, GPU/CPU/memory. Always present.
- `vllm:*` — the vLLM engine: tokens/s (`prompt_tokens_total`, `generation_tokens_total`), TTFT histograms,
  inter-token and e2e latency. Only appear with `REPORT_CUSTOM_METRICS=true` in the model's `config.pbtxt`
  (already enabled). **Important:** vllm_backend 25.08 only forwards counters and histograms into Triton — vLLM's
  gauge metrics (KV-cache occupancy, running/waiting in the scheduler) are not available through Triton; queue depth
  is tracked via `nv_inference_pending_request_count` instead.
- The TRT-LLM backend exposes its own `nv_trt_llm_*` metrics (batch manager, KV-cache blocks, iteration latency) —
  not on the dashboard, add them by analogy if needed.

## How to read the dashboard

- **Request latency by stage** — if `queue` is growing, the GPU can't keep up (increase `max_batch_size`, add an
  instance or GPU); if `infer` is growing, it's the model itself (longer prompts/responses).
- **TTFT p95** — what the user perceives as a "hang" before the first word; grows along with `waiting`.
- **E2E latency p95** vs **TTFT p95** — the difference shows how much time goes into generation vs waiting;
  if TTFT grows while ITL stays stable, the server is overloaded on prefill (queueing); if ITL grows, it's overloaded on decode.
- **Batch efficiency** = 1 for vLLM (it batches internally, Triton sees one request at a time) — this is normal;
  for TRT-LLM/non-LLM models with dynamic batching it should be > 1.

The dashboard is generated by a script (`monitoring/grafana/dashboards/triton-llm.json`), the `$model` variable
filters by model, refresh is 5s. Prometheus retains 2 days of data — stand up your own for production.
